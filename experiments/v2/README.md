# v2: full-month queues can invalidate a passing average-cost model
2026-11-02. Architecture-neutral **analytical simulation**, not a language-model benchmark, GPU measurement, or AGI claim. Prior v0/v1 are unchanged. Baseline read from private repository commit `4835447ee4e0ec812933589e3c1ef77ed0e472a9` before choosing this experiment.

## Meaningful new finding
v1 found the aggregate throughput required for a target margin but did not simulate arrival times. Here **the same monthly work at the same hypothetical serving speeds passes the margin calculation while missing latency by hours when users' activity is concentrated**.

The modeled pool costs **$220,631.04 per 30-day month**. It needs at least **913 subscribers** to support a 30% contribution-margin scenario on $500 tax-inclusive revenue, after a $50/user non-serving reserve. At 913 subscribers:

| Exactly the same workload | Decode calendar utilization | p95 first visible token | Within 60-second first-visible SLO | Scenario cost/user |
|---|---:|---:|---:|---:|
| Smooth arrivals across 24 hours/day | 70.45% | 50.73 seconds | 100% | $291.66 |
| Smooth arrivals within the same 8 hours/day | 70.45% | **30,490 seconds (8.47 hours)** | **0.102%** | $291.66 |

Both rows have identical tokens, model assumptions and hardware. The second keeps computing after users' 8-hour arrival window; no requests are dropped or tokens shortened. Its queue drains before the next day, but its latency is unacceptable under the predeclared illustrative SLO. Calendar-average throughput and an apparently positive margin are not sufficient deployment criteria.

At these operating points the within-arrival-window throughput capacity is approximately **1,296 users for 24-hour arrivals**, or **432 users for an 8-hour common window**, before tail-latency headroom. The 913-user economic minimum and 432-user peak capacity do not overlap. Merely multiplying identical always-on replicas scales both numbers and does not fix that ratio. This is specific to the assumed allocation and workload, **not a universal impossibility theorem**. Faster measured service, cheaper infrastructure, justified dynamic placement, or a genuinely geographically distributed subscriber trace could change the result. Do not move users' requests to inconvenient times and call that preserved service.

## Fixed workload and latency contract
Each subscriber submits exactly 2,000 requests over 30 days, each with 5,000 input tokens, 1,000 hidden reasoning tokens and 1,000 visible tokens: **10M input + 2M hidden + 2M visible**. Counts are conserved in every scenario. Request lengths and arrival shapes are synthetic and deliberately simple, not the user's observed workload. All users share an arrival window; deterministic phase offsets smooth the arrivals inside it. Random bursts, variable lengths, retries and outages could worsen tails. Conversely real geographic/time diversity may smooth them; it must be measured, not assumed.

Illustrative SLO chosen before running: p95 first **visible** token <=60 seconds; decode inter-token interval <=50 ms. A model-generated hidden token is not a visible answer. Even without queueing, 1,000 hidden tokens at20tokens/s consume50seconds; the first visible token takes50.725seconds including prefill, transfer and its own decode. A stricter first-visible SLO would reject this operating point regardless of aggregate token throughput.

Requests have independent contexts (5k input, growing to7k total); there is no history truncation, caching or prompt reuse in this experiment. The v1 context/weight-memory gates still apply separately. Token totals alone do not establish task equivalence, useful answer quality or sufficient reasoning.

## Serving model and accounting
- One prefill replica and one decoding replica, **32 H100 SXM 80GB each**, 64 GPUs total. Separate replicas make concurrency explicit; no free prefill/decode overlap is credited to a shared set of GPUs.
- Hypothetical prefill8,000tokens/s, a serial FCFS prefill queue with backpressure; decode100 slots at exactly20tokens/s each, FCFS admission and no preemption. Prefill is admitted just in time for the earliest free decode slot using the assumed fixed service durations; requests wait as raw input rather than accumulating an unbounded queue of prefetched states. At most one prefill and, under the default625ms prefill/50ms transfer, one transfer are in flight, in addition to the100decode slots. Raw queued inputs require host memory/storage; even all2.4M requests in the largest case at5k32-bit tokenIDs total48GB payload, before object/metadata overhead. Real host allocation and queue limits still need measurement. This idealized look-ahead scheduler requires measurement against real variable-length workloads. Aggregate decode2,000tokens/s is a target assumption, **not measured or inferred from parameter count**. No batching efficiency curve is estimated: slot capacity already assumes a measured operating point will eventually support it. The fixed service simplification is optimistic about interference, routing and heterogeneous lengths.
- Transfer between phases takes50ms, assumed uncongested. With v1 latent-attention state120layers×576values×2bytes/token, a5k prefix is691.2MB; transferring it in50ms requires13.824GB/s payload bandwidth for that request, before protocol overhead. Real transfer contention and duplication must be measured. There is no claim that independently rented nodes provide this fabric.
- At illustrative3T total parameters, 4bit payload plus15% scale/packing overhead is1.725TB per replica, **3.45TB for two copies**.32×80GB minus weights and8GB/card workspace leaves579GB each.100 decode sequences at7k context use96.77GB under the v1 latent-attention formula. This merely passes a memory gate. Full-GQA, larger context, recurrent-state size, activations and temporary buffers can alter feasibility. Recurrence/hybrid variants must use actual state dimensions; they receive no automatic quality/speed advantage.
- Active parameters and expert routing determine compute, but are not a hidden speed multiplier here. Neither dense nor top1 MoE nor another neural family is granted the hypothetical rates. The experiment accepts only an operating point, and cannot select an architectural winner.
- Rate input is **$3.99/GPU/hour**, plus20% infrastructure uplift,720hours for this exact30-day trace. Full pool cost is allocated across subscribers, including all idle time. **No second utilization divisor** is applied. Work extending beyond the month is paid until all requests drain.
- Consumer price500/(1+.20)=$416.67 net sales.30% target leaves$291.67 totalcost; subtract50 reserve gives$241.67 servingallowance. This is a contribution-margin scenario, not proven all-in netprofit. Reserve must cover real paymentfees, support, tools, failures, salaries and **amortized training/R&D**; these remain unmeasured. The20% infrastructure uplift must actually cover incremental storage/network/operations. Nonrecoverable infrastructure tax must be added, not assumed away. Training cannot be silently amortized tozero.
- Dedicated hosting corresponds to one subscriber funding the entire pool (~$220,681 includingreserve), so is nowhere near500. Pooled hosting is essential in this scenario, but not sufficient.
- £200/£20 stretch rows use v0's explicit **scenario exchange rate £0.80/USD**, not a currentFX quote. With the unchanged50-dollarreserve, £200 requires2,303subscribers (beyond even24hcapacity); £20 has no positive servingallowance. These reject only this operatingpoint/reserve, not everypossibleproduct.
- The user's illustrative $10,000 API retail usage versus500subscription is a20× **retail-price ratio**, not measured hardwareexpense or verifiedprovider subsidy. These token counts have not been shown to equal$10,000 retail usage or AGI capability.

## Primary-source evidence and limits
Accessed2026-11-02:
- [Lambda's own instance table](https://lambda.ai/instances) lists8-GPU H100 SXM80GB at3.99/GPU-hour, plusapplicabletax. No capacity reservation or inter-node fabric quote was obtained. No purchases/rentals occurred.
- [DistServe, OSDI2024](https://arxiv.org/abs/2401.09670) separates prefill and decoding and evaluates goodput under per-phase latency targets. It motivates modeling phases and queues, but its reported speedups are **not** imported into this3T scenario.
- [TaiChi,2025](https://arxiv.org/abs/2508.01989) compares aggregation and disaggregation under different TTFT/TPOT objectives. Its findings argue against treating disaggregation as universally superior. The two-replica model here is a transparent accounting case, not an architecture recommendation.
- [DeepSeek-V3 technical report](https://arxiv.org/abs/2412.19437) documents671Btotal/37Bactive and primary capability evaluations. It remains a sparse-transformer precedent, not proof that a3T variant or the assumed throughput achievesAGI. v1's controlled8B SSM/transformer/hybrid evidence remains relevant; no new matchedquality result was produced here.

## Next discriminating measurement
Before choosing any transformer/SSM/recurrent/linear-attention/hybrid/MoE winner, obtain a fixed useful-workload trace with agreed quality and first-visible/inter-token SLOs; benchmark complete candidate serving systems with actual context/state sizes and routing. Record a **goodput frontier** (requests meeting both latency targets) versus cost, not a peak aggregate tokens/s number. Measure combined versus separated phase scheduling at the same memory budget and quality. Feed measured arrival/length/rate curves into a richer simulator before claiming sustainable subscriber counts. Do not count fewer tokens, shorter contexts or weaker answers as savings.
