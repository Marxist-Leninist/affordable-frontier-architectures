# v22 economics and source audit, 2026-11-05 08:22 UTC

## New bounded finding

Restoring the original full-month subscription ledger exposes a capacity-versus-margin gap obscured by v21's short subscription paragraph. The 10M input +2M visible +2M hidden tokens/month/user baseline from v1–v4 is preserved. It is distinct from v21's mixed API ledger, which contains an additional 5M cached input. Neither represents measured customer usage or establishes $10,000 of alternative retail spend.

A hypothetical 64-H100 pool (32 prefill +32 decode, no speculative draft) at $3.99/GPU-hour, 720 paid hours and 20% infrastructure uplift costs $220,631.04/month. This is v2's pool shape, not v3's 72-GPU draft setup or a deployment quotation. At $500 gross including assumed 20% tax, and assumed payment fees of 3% of gross, net revenue is $401.6667. Net revenue here excludes sales tax and payment fees; neither is deducted again from expenses. With $150/user/month other-cost reserve and a 30% margin on net revenue, serving allowance is $131.1667 and at least **1,683 subscribers** are needed (break-even alone: 877). The old $50 reserve sensitivity needs 955 (break-even 628).

At 1,683 subscribers with the unchanged workload arriving in an 8-hour daily window, minimum aggregate prefill is **19,479 tokens/s** and generated decode **7,792 tokens/s**, before any queueing or failover allowance. Compressing the same work into a 4x correlated arrival burst requires **77,917 prefill and 31,167 decode tokens/s**. The hypothetical old 8k prefill/1.5k decode operating point supports only 691/324 subscribers in the uniform 8-hour window, or 172/81 full subscribers in that burst. These are necessary analytical gates, not measured performance. No model passes them here.

Costs charge all 720 paid hours once; capacity uses active-window seconds once. There is no additional utilization divisor, and a burst does not reduce the hardware bill. Requiring 25% capacity headroom would multiply the required throughput by 1/0.75; adding a physical spare replica instead requires its actual cost and revised capacity, not both generic penalties without justification.

## Fixed workload and tail assumptions

Baseline: 2,000 sessions/user/month, each 5,000 prompt +1,000 visible +1,000 hidden tokens, context rising to 7,000. Hidden tokens always consume work. Uncached base case is retained; 50% cached-input sensitivity keeps 10M total input and assumes cached work equals 10% of fresh work. Cache lookup/storage and suffix attention must still be measured.

Explicit **assumed** population sensitivity: 80% of users at 0.5x baseline (typical/median: 5M input +1M visible +1M hidden, 1,000 sessions), 15% at 2x (20M +4M +4M, 4,000 sessions), and 5% heavy at 6x (60M +12M +12M, 12,000 sessions). Weighted average remains exactly the original full baseline, with multiplier variance 1.6. This is an additional variability scenario, not a reduction in the baseline entitlement or a measured usage distribution. Each session retains context and generation work. The base-case calculations also apply to a homogeneous population with every subscriber receiving the full original ledger. At the $150 reserve boundary and uniform window, a linear busy-work allocation is about $131.09 for the average versus $786.56 for a 6x heavy user, before reserve: pooled 30% margin does not imply positive individual heavy-user margin.

At assumed 20 generated tokens/s per stream, 7,792 aggregate decode needs at least 390 concurrent streams; the 4x burst needs 1,559. These are concurrency lower bounds, not latency certification. Each 1,000 hidden-token preamble alone takes 50s at this speed before visible generation, so a short first-visible latency objective cannot be assumed. Preserve the previously required quality and latency conditions; no queue-time pass is claimed. Tool workload assumption for future traces: one external tool call per session, with its actual time and charge entered separately. This addition has not been measured and no tool provider was invoked.

The $150 reserve explicitly must cover tools, support, training/R&D including failed runs and evaluation, reliability expenses not in hardware, persistent storage/network not in uplift, and other overhead. It is a placeholder, not evidence those costs fit. Tool token work is counted in input/hidden ledgers only when actually included in their traces; any extra tokens must be added. No free tool work, zero amortized training, or unlimited use is asserted. Actual all-in cost must be <=70% of net revenue; merely equaling net revenue is break-even.

GBP200 and GBP20 stretch tiers remain separate. At inherited scenario GBP0.80/USD (not a current FX quote), the same $150 reserve gives negative serving allowances (-$9.42 and -$135.94). This rejects only this cost scenario, not all possible products. No currency substitution or quality reduction is counted as success.
